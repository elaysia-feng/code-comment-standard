# 代码注释规范

## 何时使用

凡是任务会实际新增、编写、修改或重构 Java / Python 代码，都自动应用本规范，
无需用户额外说"加注释"。修改代码时同步检查本次涉及的类、方法和函数，使新增或
受影响的注释符合规范。

用户显式要求"加注释 / 补注释 / 写 Javadoc / 写 docstring / 加步骤编号"，或者指出
注释违规（"TODO 没标负责人"、"类缺 Attributes:"、"复杂方法没拆步骤"等）时，
也按本规范生成或检查注释。

纯只读的代码审查、PR review、代码解释，以及不涉及 Java / Python 的编码任务不自动
触发。如果只读审查之后需要实际修改 Java / Python 代码，从开始修改时应用本规范。
用户明确要求不新增或不修改注释时，以用户要求为准。

以下场景不强制套用：单元测试的简单夹具与断言方法、框架或 IDE 生成的样板代码
（如 Lombok）、一次性脚本与教学示例代码。

## 动手前必读

遇到下列情况，**先 Read `references/examples.md` 对照模板再写**，不要凭记忆：

- 本次会话第一次生成带步骤编号注释的方法
- 方法有 3 个以上步骤，需要确认二级编号（1.1、1.2）的排版
- 要写类注释、生成器 docstring、或并列分支的编号

规则条文在本文件，可直接抄写的完整代码在 `references/examples.md`，两者配套使用。

## 一、总体原则

1. 注释解释**为什么**这样做，而不是简单复述代码在做什么。
2. **所有注释必须使用中文（硬性规定）**：Javadoc、docstring、步骤编号注释、TODO
   的说明文字一律用中文书写；确需出现的英文专有名词（类名、方法名、HTTP 状态码、
   协议术语等）可原样保留，但注释句子本身必须是中文。
3. 所有 public 类、方法/函数必须有文档注释（Javadoc / Docstring）。
4. 方法体内逻辑较复杂（分支多、步骤多、涉及业务规则）时，使用**步骤编号注释**拆解流程。
5. 简单的 getter/setter、单行逻辑方法，**不强制**使用步骤编号，避免注释冗余。
6. 注释需要跟随代码同步更新，禁止出现过时或误导性注释。

## 二、方法级文档注释规范

### 2.1 Java：Javadoc

所有 `public` / `protected` 方法必须包含 Javadoc：

| 标签 | 说明 |
|------|------|
| 摘要行 | 一句话概括方法作用（名词/动词短语，不要求完整句子） |
| `@param` | 每个参数的含义、取值范围、是否允许为 null |
| `@return` | 返回值含义；void 方法可省略 |
| `@throws` | 可能抛出的受检异常及触发条件 |

### 2.2 Python：Google Style Docstring

所有 public 函数/方法必须包含 docstring，结构固定为：

| 小节 | 说明 |
|------|------|
| 摘要行 | 一句话概括函数作用 |
| `Args:` | 每个参数的含义与取值约束 |
| `Returns:` | 返回值含义；生成器改用 `Yields:` |
| `Raises:` | 可能抛出的异常及触发条件 |

### 2.3 类注释

- Java：类上方使用 Javadoc，说明类职责、是否线程安全、典型使用方式
- Python：类的 docstring 说明类职责，如有公共属性用 `Attributes:` 列出

> 完整可对照抄写的 Java / Python 示例见 [references/examples.md](references/examples.md)。

## 三、步骤编号注释约定

### 3.1 何时使用

判定标准与校验脚本保持一致，满足**任一**条件即为复杂方法，必须用步骤编号拆解：

- 方法体 **≥ 20 行**（不含 Javadoc / docstring）
- 或方法体 **≥ 10 行**，且 **分支/循环/try 合计 ≥ 3 个**
  （Java 数 `if` `for` `while` `switch` `try` `catch` `do`；Python 数 `if` `for` `while` `try`）

不需要使用的场景：

- 方法体**不足 10 行**的短方法一律豁免（如简单的字段映射、单个条件判断）
- 一眼就能看懂的线性代码

> **嵌套函数 / 嵌套类是否计入阈值**：方法体内定义的内部函数（``def``、``async def``）
> 与局部类（``class``）属于实现细节，**不计入**外层方法体的长度与分支数；同理 Java
> 内部类、匿名类里的逻辑也不计入。校验脚本（`_is_complex_python` /
> `_is_complex_java`）按此语义实现。

> 上面是可机械判定的**下限**，用于和脚本对齐。方法虽未达阈值、但确实有 3 个以上
> 值得交代的执行阶段时，仍然鼓励加编号——脚本不会因为"多写了"而报警。

### 3.2 编号规则

- 顶层步骤用 `// 1.`、`// 2.`、`// 3.` ...，按执行顺序编号（Python 用 `#`）
- 子步骤用 `// 1.1`、`// 1.2` ...，最多建议到二级，避免层级过深影响可读性
- 每个编号注释应为**一句话**，说明该步骤的目的，而不是重复代码
- 编号必须与实际执行顺序一致；调整代码顺序时同步调整编号
- 分支逻辑（if/else、switch）如果本身是某一大步骤的子项，用子编号；
  如果分支代表并列的独立步骤，可用同级编号 + 简要说明
  （分支编号写法见 [references/examples.md](references/examples.md) 第三节）
- 复杂方法体内**至少要有 2 条**步骤编号注释才算完成拆解；只写一条 `// 1.` 等于没拆，
  校验脚本同样会判定为未拆解

### 3.3 与 Javadoc/Docstring 的关系

- Javadoc / Docstring 面向**调用者**，描述"这个方法能做什么"（外部视角，黑盒）
- 步骤编号注释面向**维护者**，描述"这个方法内部怎么做"（内部视角，白盒）
- 两者不能互相替代，复杂方法应同时具备

## 四、其他通用约定

### 4.1 TODO 注释格式

必须标注负责人，方便追踪，禁止无主 TODO：

```java
// TODO(zhangsan): 支付超时后需要补充自动关单逻辑，预计 v2.3 版本处理
```

### 4.2 禁止的注释写法

不要写没有信息量、纯复述代码的注释：

```java
int count = 0; // 将 count 初始化为 0（禁止）
count++;       // count 加一（禁止）
```

## 五、生成代码时的检查清单

写完代码后，对照自查：

- [ ] 所有注释是否使用中文书写（专有名词可保留英文）
- [ ] public 方法是否有完整 Javadoc / Docstring（含 Args/Returns/Raises）
- [ ] public 类是否有 Javadoc / Docstring（说明职责、线程安全性）
- [ ] 复杂方法（达到 3.1 阈值）是否有步骤编号注释，且**不少于 2 条**
- [ ] 编号是否与实际代码执行顺序一致
- [ ] 是否存在废话注释 / 过时注释
- [ ] TODO 是否标注了负责人

## 六、自动校验脚本

`scripts/check_comments.py` 用规则做静态检查，覆盖上面清单里客观可验证的部分：

| 规则 | 级别 |
|------|------|
| public 方法/函数缺少 Javadoc / Docstring | ERROR |
| TODO 未标注负责人 | ERROR |
| 有参数但文档缺 `@param` / `Args:` | WARNING |
| 有返回值但文档缺 `@return` / `Returns:`（生成器写 `Yields:` 也算） | WARNING |
| 复杂方法（≥20 行 或 ≥3 个分支/循环/try）缺少步骤编号注释 | WARNING |

判定细节：

- 方法长度按**方法体**计算，不含 Javadoc / docstring
- 方法体不足 10 行的短方法一律豁免步骤编号要求，对应上面 3.1 的"短方法不需要"
- 复杂方法体内需出现**至少 2 条**编号注释才算已拆解
- **方法体内嵌套的函数 / 局部类不计入**外层方法的长度与分支数；只统计外层自身
  的 `if`/`for`/`while`/`switch`/`try`/`catch`/`do`（Python 不含 `switch`）
- TODO **不区分大小写**，`# todo:`、`# TODO:` 都算；但必须写成 `TODO(负责人): 说明`
  才不会报警
- TODO 只在注释中统计，字符串常量和 docstring 里的字样不会误报
- 下划线开头的 Python 函数视为非 public，不做要求
- Java text block（`"""..."""`，自 Java 13 起）整体视为字符串，里面的 `/* */`、
  `/** */` 不会被误识别为注释或 Javadoc
- Javadoc 内容里出现的字面量 `/* foo */`（例如 `{@code /* foo */}`）不会被误判为
  块注释结束；脚本按 `{@...}` 内联标签的嵌套深度判断 `*/` 是否应当关闭块

脚本**不覆盖**的规则，需要人工检查：

- Java **类**的 Javadoc（脚本只扫方法；Python 类的 docstring 有检查）
- `@throws` / `Raises:` 是否完整
- `@param` / `Args:` 只检查"有没有"，不校验条目数与参数个数是否匹配
- 废话注释、过时注释（无法静态判定）
- 注释语言是否为中文（脚本不做语言判定，人工检查）

**每次生成或修改 Java/Python 代码文件后，主动运行这个脚本自查一遍**，
根据输出修正后再交付给用户：

```bash
python3 scripts/check_comments.py <改动的文件或目录>
```

Windows 上如果没有 `python3`，用 py 启动器：

```bash
py scripts/check_comments.py <改动的文件或目录>
```

脚本不依赖第三方库，Python 3.8+ 即可运行；不在 skill 目录下执行时，把
`scripts/check_comments.py` 换成脚本的绝对路径。

退出码：

- `0` —— 没有 ERROR（可能仍有 WARNING，建议尽量处理，但不强制）
- `1` —— 存在 ERROR，必须修正
- `2` —— 没有匹配到任何 `.java` / `.py` 文件（targets 路径无对应源文件），
  通过 stderr 提示；用于和"无 ERROR 的干净通过"区分

注意：这是基于正则/AST 的启发式检查，不是完整语法分析，Java 部分对复杂泛型、
内部类等场景可能有误判。脚本结果作为自查辅助，不能替代人工判断。

### 6.1 标准工作流

每次生成或修改 Java / Python 代码后，按顺序走完：

1. 对照第五节清单自查一遍
2. 运行脚本：`py scripts/check_comments.py <改动的文件>`
3. 输出形如 `src/UserService.java:42: WARNING [missing-param] 有参数但 Javadoc 缺少 @param`，
   按"路径:行号"定位
4. **ERROR 必须清零**后才能交付
5. WARNING 逐条判断：确属遗漏就补；若是启发式误判（如复杂泛型、内部类），
   在回复里说明原因，不必强行消除

交付前告知用户脚本的实际运行结果，不要跳过第 2 步直接声称"已符合规范"。
